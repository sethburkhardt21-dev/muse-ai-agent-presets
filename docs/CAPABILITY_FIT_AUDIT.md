# Specialist capability fit audit — post-alpha source increment

**Scope:** all eleven neutral presets and one separate finder service. This audit compares intended responsibilities with the **public shell** and the capabilities expected from separately maintained donor systems. The listed donor families describe review targets, not incorporated code or permission to redistribute it. No native Muse invocation, private model, licensed asset, or live external integration is asserted.

## Evidence grades

- `PLAYBOOK`: a tested, role-specific, source-only procedure, not an executable host tool.
- `LOCAL_SLICE`: a tested, newly written offline reference function, not the full donor engine.
- `DONOR_CANDIDATE`: separately implemented code exists, but is not admitted into this public repository.
- `HOST_UNBOUND`: no recipient Muse account, registered skill, subchat, Space or external authorization verified.

## Portfolio checks

A healthy collection requires more than every preset having files:

1. **Coverage:** every specialist has a mission, three non-duplicated methods, evidence and refusal rules, a first negative-control canary, and a default-disabled suggested reviewer handoff. The catalog doctor validates these properties.
2. **Differentiation:** building a candidate, independently examining it, finding evidence, adjudicating a claim, and coordinating work are distinct roles. Their outputs and authority must not collapse into one self-certified agent.
3. **Minimal duplication:** use common read-only provenance and receipt schemas; do **not** copy eleven tool registries, credential stores, schedulers, or private memory databases.
4. **Rights:** no donor source moves into the public tree until file-level origin, license, secrets, assets and test provenance are reviewed. Public third-party skills are linked or adapted item-by-item; not copied wholesale.
5. **Runtime integrity:** the receiving Muse/Hatch account, SDK and real callable host methods govern every grant. No source file claims original native execution.

## Work queue: prioritized by functional value and integration risk

**A — Native-install diagnostic:** on a separately authorized disposable Muse account, prove the file-loader, skill discovery, optional hooks and harmless read-only tool call. Preserve user state and source identity. This is the critical path for all presets.

**B — Garden transaction vertical:** start with the owner-scoped approval and revision-fenced seasonal batch semantics. Port the minimal source/contract after a per-file rights audit. Validate original source tests, new cross-account cases, migration/restart, and native UI readback.

**C — Learning evidence vertical:** install a nonclinical document→quote→draft→grade→due-review path with wrong-learner/replay negatives. Do not import held clinical question banks or claim learning efficacy.

**D — Model Builder / Research Evaluator pairing:** one authorized small training candidate and genuinely independent held-out exam, with exact artifact identity and preserved failures; never reuse consumed final items.

**E — Claims / Finder / Reverse Research:** deliver separate provenance and decision surfaces; scope PCAP and UI reconstruction to owned toy fixtures; prove no unsafe external effects.

**F — Other specialist execution paths:** bring in engineering review, creative rendering, personal assistant workflows and coordinator recovery only after the host contract is proven. Every role has its own native canary.

## Limits of this audit

It reviews publicly shipped role coverage and the current documented donor interfaces. It does **not** re-run all original private donor suites or assert that the donor's present live branch is healthy. That requires a separate pinned inventory and independent changed-seam qualification before any source transfer. Passing the role playbook tests earns only `PLAYBOOK`, not `HOST_WIRED` or model competence.
