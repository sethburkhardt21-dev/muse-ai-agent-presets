# Muse Specialist Toolkit — 30-day V1 observation

The purpose of V1 is to demonstrate existing working value and learn what people use. This is an owner-controlled measurement guide, not a service or an automated activity.

## Capture real observations

| Signal | Grounded source | Decision supported |
| --- | --- | --- |
| Repository visitors and unique clones | GitHub Insights → Traffic | Are people discovering and trying the toolkit? |
| Referrals and popular pages | GitHub Traffic | Which entry points attract relevant users? |
| Release asset downloads | GitHub release | Are people using tools, starters or the connector directory? |
| Stars, forks, issues | GitHub repository | Interest and willingness to participate |
| Reproducible onboarding failures | Issue reports | What needs improvement before adding breadth? |
| Requests for particular specialists | Actual user feedback | Which workbench deserves deeper investment? |
| Connector requests and broken setup links | Actual feedback | Where to add verified guidance or integrations? |

GitHub Traffic is a rolling 14-day view. Save dated baseline results, then observe at approximately two and four weeks. Do not invent counts or infer actual installations from a star.

## Decision criteria

If people discover the repo but fail onboarding, repair onboarding. If a particular specialist has repeatable demand, develop its unique workflow. If connectors dominate, improve installation quality. If users need tasks the current library lacks, add targeted reviewed skills rather than bulk importing to increase the number.

If adoption is low, investigate distribution, discoverability and realistic demonstrations before changing architecture.

Do not automatically start a scheduled monitor, outreach campaign or other external effect without explicit authorization. Preserve V1 while gathering evidence.
